# Миграции базы данных

## Цель

В проекте используется единый стек хранения и миграций:

- `SQLAlchemy` — описание моделей и работа с ORM;
- `Alembic` — версионирование схемы базы данных;
- `PostgreSQL` — целевая СУБД;
- `entrypoint.sh` -> `alembic upgrade head` — автоматическое применение миграций при старте runtime.

## Единый принцип

Источник истины по структуре данных состоит из двух слоев:

1. SQLAlchemy-модели в `api/app/models/`
2. Alembic-миграции в `api/migrations/versions/`

Модель без миграции считается незавершённым изменением.
Миграция без отражения в модели считается техническим долгом.

## Структура

```text
api/
  app/
    core/
      config.py
      db.py
    models/
      base.py
      lead.py
      chat.py
    schemas/
      ...
  migrations/
    env.py
    versions/
      20260429_0001_initial_schema.py
  alembic.ini
```

## Текущий процесс

При старте API-контейнера выполняется:

```bash
alembic upgrade head
```

Это гарантирует, что runtime поднимается только после попытки привести схему к актуальной версии.

## Правила ведения миграций

### 1. Любое изменение модели требует миграции

Если изменяется хотя бы одно из следующих свойств, нужна новая миграция:

- новая таблица;
- новый столбец;
- изменение типа столбца;
- изменение nullable/unique/index;
- внешний ключ;
- rename колонок или таблиц;
- удаление полей или таблиц.

### 2. Не редактировать старые применённые миграции

После того как миграция попала в общую ветку или уже была применена в чужой среде:

- не переписывать её содержимое;
- не менять `revision`;
- не менять `down_revision`;
- не использовать `git commit --amend` для уже опубликованной схемы.

Исправления делаются только новой миграцией.

### 3. Одна логическая задача — одна миграция

Нельзя смешивать в одной миграции несвязанные изменения схемы.

Хорошо:
- новая таблица лидов;
- отдельно индексы под аналитику;
- отдельно новая таблица событий.

Плохо:
- одновременно лиды, AI-сессии, chat events и произвольные cleanup-операции.

### 4. Downgrade должен быть осмысленным

Для каждой миграции обязан существовать рабочий `downgrade()`.

Исключение допустимо только для сознательно необратимых операций, но тогда это должно быть отдельно задокументировано в самой миграции и в release notes.

### 5. Переименование делать явно

Не выполнять rename через удаление и повторное создание таблицы, если нужно сохранить данные.

Для rename использовать явные SQL/Alembic-операции и заранее продумывать:

- сохранность данных;
- обратимость;
- время блокировок;
- совместимость с текущим кодом.

### 6. Изменения данных отделять от изменений схемы

Schema migration и data migration лучше разделять.

Если требуется backfill:
- сначала ввести новую схему;
- затем выполнить контролируемую миграцию данных;
- затем перевести приложение на новую логику.

## Рекомендуемый цикл работы

1. Изменить SQLAlchemy-модель.
2. Создать новую Alembic-миграцию.
3. Проверить `upgrade()` и `downgrade()` вручную.
4. Применить миграцию локально.
5. Проверить запуск API и smoke-сценарий.
6. Только после этого коммитить код и миграцию вместе.

## Локальная проверка

Проверить конфиг:

```bash
docker compose -f docker-compose.yml config
```

Поднять стек:

```bash
docker compose -f docker-compose.yml up -d --build
```

Проверить, что API прошло миграции и отвечает:

```bash
curl -f http://127.0.0.1:26800/api/v1/health
```

## Что запрещено

- держать одновременно ORM и raw-schema flow как два разных источника истины;
- применять схему через `metadata.create_all()` в production runtime;
- вносить schema-изменения вручную в базе мимо Alembic;
- редактировать таблицы напрямую без соответствующей миграции;
- коммитить model change без migration file.

## Архитектурная позиция проекта

Для этого репозитория принимается единый стандарт:

- data layer строится вокруг `SQLAlchemy`;
- миграции ведутся через `Alembic`;
- контейнерный runtime применяет `alembic upgrade head`;
- документация и код должны описывать один и тот же migration flow.
