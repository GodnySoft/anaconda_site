# Аудит и план нормализации проекта

## Статус

Проект уже не находится в нулевой фазе: локальный runtime, data-layer и базовый public MVP-контур собраны. Однако репозиторий ещё не доведён до состояния, которое можно считать аккуратным production-grade основанием для дальнейшей разработки и релизов.

Текущее положение:

- продуктовый этап: конец **Этапа 1 / Public MVP**;
- инженерный этап: **фаза нормализации репозитория и выравнивания инженерного контура**.

## Подтверждённые сильные стороны

- есть рабочая modular frontend-структура;
- есть единый `SQLAlchemy + Alembic` migration flow;
- есть локальный Docker runtime;
- есть набросанный release-based deploy через Ansible;
- есть GitHub Actions под quality/smoke/publish/deploy;
- есть отдельные role-файлы и отдельная память проекта.

## Подтверждённые дефекты

### 1. Git-индекс в аномальном состоянии

Сейчас `git status` показывает массовые пары `deleted + untracked` по почти всему репозиторию.

Риск:

- любой автоматический commit может зафиксировать ложную историю удаления и повторного добавления файлов;
- переход на `main` и push в GitHub пока нельзя считать безопасными.

### 2. Репозиторий загрязнён generated-артефактами

Подтверждённый мусор:

- `__pycache__`
- `.next`
- bootstrap-логи и служебные runtime-файлы
- устаревшие role-артефакты

### 3. Внутренние markdown-файлы были частично испорчены кодировкой

Проблема затронула часть `dev/*` и часть docs/CI-слоя. Это подлежит отдельной нормализации и уже считается дефектом инженерного процесса.

### 4. Документация обновлялась неравномерно

Часть docs уже отражает новое состояние проекта, часть — требует чистки, переписи или хотя бы выравнивания формата.

### 5. CI/CD готов логически, но не готов процессно

Release flow подготовлен под `main`, но репозиторий и git-flow ещё не приведены к состоянию, в котором этот контур можно безопасно активировать.

## Принятый план нормализации

### Фаза A. Репозиторная гигиена

- очистка generated-мусора;
- нормализация `.gitignore`;
- удаление устаревших локальных артефактов;
- исправление битых markdown-файлов.

### Фаза B. Внутренняя документация

- нормализация `dev/project_development_memory.md`;
- нормализация внутреннего плана и role-файлов;
- выравнивание docs по CI/CD, deploy и runtime.

### Фаза C. Git и веточная дисциплина

- отдельная диагностика аномального индекса;
- выравнивание worktree/index;
- только потом ввод `main` и реальный release flow.

### Фаза D. Закрытие Этапа 1

- ручная QA `/` и `/contacts`;
- финальная доводка public surface;
- сверка с `dev/v1`;
- фиксация Definition of Done по Public MVP.

### Фаза E. Production readiness

- подтверждение secrets и host prerequisites;
- dry-run deploy/rollback;
- запуск реального release процесса после перехода на корректный git-flow.

## Что уже сделано в текущей нормализации

- создана отдельная роль главного дизайнерского агента;
- начата нормализация внутренней памяти проекта;
- выявлены и подтверждены generated-артефакты и кодировочные дефекты;
- подтверждено, что часть CI/CD-документации и workflow-описаний требует очистки.

## Следующий обязательный шаг

Следующий обязательный шаг после текущей итерации — **выровнять git-состояние репозитория**, потому что без этого нельзя безопасно переходить к настоящему release-циклу через `main`.
## Дополнительные результаты текущей итерации

### Что уже приведено в порядок

- репозиторий очищен от generated-мусора первого уровня;
- удалена устаревшая роль `dev/roles/designer_role.md`;
- нормализованы ключевые внутренние markdown-документы;
- исправлен ручной workflow production-операций;
- нормализован `.gitignore`.

### Что подтверждено повторной runtime-проверкой

После очистки и нормализации проект снова подтверждён локально:

- `docker compose -f docker-compose.yml config` проходит;
- `docker compose -f compose.prod.yml --env-file .env.prod config` проходит;
- `docker compose -f docker-compose.yml up -d --build` проходит;
- `/api/v1/health` отвечает `200`;
- `/` и `/contacts` отвечают `200`.

### Что дополнительно обнаружено по git

Подтверждено, что в `.git/config.worktree` включён `sparse-checkout` с нестандартным исключением старого role-файла. Это может быть связано с текущей аномалией `deleted + untracked`, и этот след нужно исследовать до любых реальных коммитов.

### Что дополнительно обнаружено по зависимостям

Во время Docker-пересборки frontend-контейнера `npm install` сообщил о `8 vulnerabilities` (`1 moderate`, `6 high`, `1 critical`). Это формирует отдельную задачу на dependency-аудит и обновление пакетов.
